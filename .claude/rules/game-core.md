# Game Core (Govern.Core)

`Govern.Core` is the pure, deterministic game engine. The server uses it to validate moves authoritatively, and the Blazor client uses it to preview them from a `PlayerView`. Behaviour and rules are in `docs/features/game-core.md`; the reasoning is in `docs/decisions/0004-game-engine.md`.

## Purity (enforced)

- **Base class library only:** no project references, no `PackageReference` (`ProjectReferenceTests.Core_HasNoPackageReferences`) and no `Microsoft.*` types (`LayerDependencyTests.Core_DependsOnlyOnBaseClassLibrary`). Core does not use `Govern.Utils`: it has its own `RuleViolation`/`CommandResult`, and Application maps `RuleViolation` to `Error`. (`RuleViolation`, not `GameError`, so the name never clashes with the Application feature's `GameErrors` or with `Utils.Results.Error`.)
- **No I/O, clock, async or `System.Random`** (`Core_DoesNotUseNondeterministicOrIoApis`). **No `Guid.NewGuid`, `Guid.CreateVersion7` or `GetHashCode(`** (`Core_DoesNotCreateIdentifiersOrUseHashCodes`). Logging and DI are also out (no `Microsoft.*`). Randomness goes through `DeterministicRandom`, whose state lives in `GameState.RngState`; new unit and city ids come from the same generator (`GameState.AllocateId`), hashed with SHA-256. **Never send raw `DeterministicRandom` output to a client** (SplitMix64 is invertible: two raw values reveal `RngState`); hash it (`DeterministicRandom.NextHashed`), or expose only a few bits of a small range. Never add a counter an opponent could read activity from. `GameFactoryTests.Create_Ids_AreNotRawGeneratorDraws` guards the ids. The same state, actor and command must always give the same result; order-dependent code sorts explicitly.

## State and rules

- `GameState` and everything in it are immutable records. Change them with `with` and the `internal` `GameState.WithUnit`/`WithoutUnit`/`WithCity`/`WithPlayer`/`AllocateId` helpers. Collections are `ImmutableArray` so the JSON stays plain.
- **Only `GameEngine.Execute` changes a game.** Adding an action means:
  1. one `Actions/XxxAction.cs` holding the `XxxCommand` record and the `internal static class XxxRule` with `Apply(ruleset, state, actor, command) → CommandResult`;
  2. its `[JsonDerivedType]` on `Engine/GameCommand`;
  3. a case in `Engine/CommandDispatcher` (a trade command in `TradeRule.Dispatch`, a science command in `ScienceRule.Dispatch`);
  4. new events in `Events/XxxEvent` plus `[JsonDerivedType]` on `GameEvent`, and new codes in `Engine/RuleViolations`.
- **Rule violations are returned as `RuleViolations.Xxx`** (a stable snake_case code) and never thrown. Throw only for programming errors: an invalid `GameSetup`, an unknown command type, a missing entity inside a rule.
- **Every game number, list and text comes from the ruleset** (`Rulesets/Ruleset`, parsed from `rulesets/<key>/vN.json`), never a constant in Core. Every engine entry point and rule takes the game's `Ruleset` as its first parameter. A new stat is a field in the JSON, its record in `Rulesets/` (or `UnitDefinition`/`TerrainDefinition`, or an `Economy/` definition), a `RulesetValidator` (or `EconomyRulesValidator`/`UpkeepRulesValidator`) check with a `RulesetTests` case, and the docs in `docs/game/game-data.md` (building sections: `game-data-economy.md`). Any rules change (a new or changed stat, unit, terrain or mechanic) also updates the player rules reference `docs/game/rules.md` in the same change; `RulesReferenceTests` (`tests/Govern.ArchitectureTests`) checks its "Terrain types", "Rivers", "Unit types", "Improvements", "City storage", "City buildings", "Costs and upkeep", "Class counters" and "Game numbers" tables against the default ruleset, and a new ability needs its label in that test. Rules check **abilities** (`UnitDefinition.CanFoundCity`/`CanAttack`/`CanRangedAttack`/`CanBuildImprovements`/`CanBuildBridges`, `AttackRange`, from `UnitAbility`) and **classes** (`UnitDefinition.Class`, for `combat.counters`), never a unit id; a new ability is a `UnitAbility` value plus its rule.
- **`UnitType`/`TerrainType` are ruleset ids** (`readonly record struct`s written to JSON as the plain id). There are no `UnitType.Settler`-style constants; tests use `Builders/TestRulesets` (the real default file, and variants via `TestRulesets.With`).
- **Clients only ever receive `GameEngine.ViewFor`** (`PlayerView`), never `GameState` or unfiltered events. Anything added to state that an opponent must not see must be filtered in `VisibilityCalculator.ViewFor`.
- **`PlayerView.Version` is an opaque fingerprint** of the rest of the view (SHA-256 of its JSON). Everything in the view is hashed, so a new view field must hold only what the viewer may see; never put `GameState.Version` or another counter into the view.
- **Rejections must not leak hidden information.** Another player's unit or city is `*.not_found`. A rule that inspects tiles or objects the actor cannot see must return the same error it would return if they were empty. Keep the fog invariants that `RulesetValidator` enforces (sight ≥ movement ÷ cheapest passable cost; `found_city` units' sight ≥ city spacing − 1; a unit with upkeep has sight ≥ `upkeep.supplyRadius` + 1) or filter by visibility. A rule that reads territory looks only at the unit's tile and its neighbours, which it always sees; the one exception, a building's site (`ProduceBuildingRule.CheckSite`), reads any tile of the city's territory and its neighbours, which is exact only because own territory is always visible and `VisibilityCalculator.UpdateExplored` always explores the ring around it (keep both, or the preview breaks and `city.building_needs_terrain` leaks an unexplored tile's terrain).
- **View shape:** `TileView` has no coordinates (tiles are row-major; use `PlayerView.CoordAt`/`TileAt`), cities in a view are `CityView`s built by `CityView.From`, with an enemy city's production null, and units are `UnitView`s built by `UnitView.From`, with an enemy unit's movement null and every seen unit's health. Never add per-tile coordinates, an opponent's production, buildings, stock, job or movement back; improvements, buildings on tiles (`TileView.Building`), bridges and `TileView.TerritoryOwner` are shown on visible tiles only, `CityView.ProducingBuildingSite` to the owner only, `TileView.TerritoryCity` on the viewer's own territory only. Any new per-object field in the view needs the same decision: everyone, owner only, or visible tiles only.
- **View previews** (`GameEngine.ReachableTiles`/`DestinationPath`/`CheckExplore`/`AttackTargets`/`CombatForecast`/`CheckFoundCity`/`CheckBuildImprovement`/`BridgeTargets`/`CheckProduceBuilding`/`BuildingSites`/`CityIncome`/`CityForecast`/`UnitSupply` over a `PlayerView`, in `Visibility/ViewPreviewCalculator` and `UpkeepPreviewCalculator`) must give exactly what `Execute` gives. They share the rules' checks (`CommandGuardRule.CheckTurn`, `AttackRule.Check`, `FoundCityRule.Check`, `BuildImprovementRule.Check`, `BuildBridgeRule.Check`, `ProduceBuildingRule.Check`/`CheckSite`, `ReachabilityCalculator`, `CombatCalculator`) instead of copying them. A new action the client should preview gets a shared check and a parity test in `Engine/` (`GameEnginePreviewTests` for moves and attacks, `BuildPreviewTests` for building: parity with `Execute` for every tile near the unit). The previews are exact only while the validator's sight invariants hold (a terrain `sightBonus` only adds sight, so it keeps them; anything that *reduces* sight, such as forests blocking it, breaks them and needs a design change first). The parity scenarios cover forest (cost 2), mountains and lake (impassable), hills (sight bonus), a range-2 archer, ships on a lake (galley, bireme) and land units on its shore, and a stream, a river and a deep river around the unit; the validator keeps a ranged unit's range within its sight; a new terrain type with a new kind of cost or blocker adds parity scenarios with it (`GameStateBuilder.WithTerrain`).
- **Combat** (`Engine/CombatCalculator`, internal) is integer maths only, so the browser's forecast equals the server's roll range. `AttackRule` rolls within `CombatCalculator`'s ranges with `DeterministicRandom.NextHashed` (damage is shown to both players); `CombatForecastTests` checks over many seeds that `Execute` hits exactly the forecast's lowest and highest damage for each kind of fight, so a new modifier adds a fight there. Health is stored as `Unit.Damage` (0 = unhurt, left out of the JSON while 0), so older games read unchanged; health = `combat.maxHealth` − damage.
- **Orders (F19, F20):** a unit's standing order is `Unit.Destination` or `Unit.Exploring` (owner only in the view). `Engine/AutoMoveRule` plans it with `Map/PathFinder` over the owner's knowledge only (explored terrain and rivers, bridges, units and cities on visible tiles), which is exactly what the `PlayerView` holds, so `GameEngine.DestinationPath` equals the rule; it walks when the order is given and at the start of the owner's turn (`EndTurnRule.PassTurn`). An explorer heads for the nearest known tile next to one the owner never saw (`Map/ExploreFinder`, the same knowledge, so `GameEngine.CheckExplore` equals the rule). Every other unit command clears the destination and the exploring; a new unit command that keeps a unit in place or moves it must do the same.
- **Movement is per step, not per tile:** `ReachabilityCalculator.StepCost` prices a step between neighbours as the entered tile's cost plus the crossing cost of the river on the edge between them (null over an uncrossable river); the rule and the view preview both use it. Rivers live on edges: `HexEdge.Between(a, b)` names the one tile that stores an edge (its east, north-east or north-west side, `Tile.Rivers`), and `GameMap`/`PlayerView.RiverBetween` look it up from either side. Bridges follow the same model (`Tile.Bridges`, `TileBridges`), and rules read a river only through `GameMap`/`PlayerView.CrossedRiverBetween` (null when the edge is bridged): the step cost, the combat river modifier and the capture check. A crossing cost only adds, so the fog invariants hold; a river that blocks sight would break them. **Domains (G15a):** a unit's `UnitDefinition.Domain` decides its ground through `TerrainDefinition.AllowsDomain` (land: `isPassable`; naval: `isWater`, never passable), inside `ReachabilityCalculator.StepCost(ruleset, domain, terrain, river)`, which every step pricer (move, preview, auto moves, trade walks) calls instead of checking `isPassable` itself; ships ignore rivers. Melee reaches only the same domain (`AttackTarget.Domain`, `attack.other_domain`); ranged reaches both. A unit's `requiresBuilding` (or an upgrade, `Ruleset.IsKindOf`) gates production; a naval unit spawns on water next to that building's tile and heals as in a city next to it. The fog invariant's cheapest cost is per domain.
- **Building (G10a, the owner's model, not a Civ copy):** units have no charges. A unit with `build_improvement`/`build_bridge` has its own `buildProduction`; a job (`Unit.Job`, `UnitJob`) gains it each end of turn, plus the production of the own city whose territory (`Tile.Territory`) holds its tile, which that city then doesn't spend (one job per city per turn, oldest first: `Engine/ConstructionRule`). A job's placement check runs again each turn and drops the job when it fails. Starting a job zeroes movement; a unit with a job can't move, walk or explore (`unit.busy`, and the previews give it no reachable tiles) until `CancelJobCommand` drops the job, so a misclick never stops a build; attacking drops it too. A city produces its unit or, when `ProducingBuilding` is set, a building (`ProduceBuildingCommand`) on a tile of its territory it reserves (`City.ProducingBuildingSite`, G10c: off the city tile, passable, free of improvements, buildings and improvement jobs, `requiresAdjacentTerrain` next to the site); a finished building joins `City.Buildings` (what every rule reads) and stands on `Tile.Building`, and a reserved or built tile takes no improvement; a city's production per turn is `CityProduction.PerTurn` (base plus buildings, itemised by `CityProduction.Sources`). New ids (`ResourceType`, `ImprovementType`, `BuildingType`) live in `Economy/` and are plain ids in JSON; their names come from `Ruleset.ResourceName`/`ImprovementName`/`BuildingName`.
- **Yields and territory (G5, G7, the owner's model):** each city keeps its own stock (`City.Stock`, ruleset order; there is no player stockpile). A tile's yield is `Economy/YieldCalculator.TileYields` (terrain + the largest river yield per resource on its edges + improvement); at the end of turn each city adds `YieldCalculator.CityIncome` (its territory's tiles + `cities.yields` + buildings), then `Engine/TerritoryRule.Grow` spends `territory.growthResource` on one more tile, chosen with no randomness. Territory lives on tiles (`Tile.Territory`, one city per tile, never taken by growth; capture keeps it). Anything the client shows about income uses the same calculator (`GameEngine.CityIncome`), so the preview equals `Execute`. **Storage (G8c):** a city holds at most `Cities/CityStorage.Caps` (`cities.storage` plus its working buildings' `storage`) of each stocked resource; End turn cuts every city's stock to it as its very last economy step (after production, both players' cities), so a new rule that adds to a stock needs no cap of its own.
- **Costs and upkeep (G8a, the owner's model):** a city pays an item's whole `resourceCost` once, when production begins (`City.ProductionPaid`; a real change of item refunds it, capture clears it), and waits while it can't. After the income, `Engine/UpkeepRule` makes each city pay, all or nothing per item, for its buildings and the owner's units on its territory in its `UpkeepPriority` (`Economy/UpkeepCalculator.Pay`); a unit off territory lives off the land within `upkeep.supplyRadius` (not split between units, nothing taken). Unpaid units lose health but never die of it; buildings have their own damage (`City.BuildingDamage`) and stop working at full damage, so production and income always use `City.WorkingBuildings`. A resource cost never uses `territory.growthResource`, which keeps `GameEngine.CityForecast` exact (its `MissingToBegin` and `ProductionPerTurn` assume the city doesn't feed a job, which the client checks); the post-upkeep building damage is `UpkeepCalculator.DamageAfter`, shared by the rule and the forecast; `Engine/UpkeepPreviewTests` checks the forecast and `UnitSupply` against `Execute`.
- **Trading (G17, reworked by G17b, the owner's model):** no money; a city with `trade.building` has a market (`City.Market`, `City.Demand`) and at most `trade.tradersPerCity` traders (`Unit.HomeCity`). Each trader carries one deal (`GameState.TradeDeals`, `TradeDeal` with a `TradeDealStatus`: proposed, countered, travelling, active; `Unit.DealId` once agreed); only agreed deals use market caps. The four deal commands are dispatched by `Engine/TradeRule.Dispatch` (a new trade command adds its case there, not in `CommandDispatcher`). A trader carrying a deal takes no other order: a new unit command must refuse it with `trade.on_deal`. **Traders share tiles** (`UnitDefinition.SharesTiles`): they never block and are never blocked, so rules ask for a tile's holder with `GameState.HolderAt`/`PlayerView.HolderAt` (or every unit with `UnitsAt`) and pick an attack's target with `AttackRule.DefenderAt` (ties by id, never list order: the state keeps creation order, the view id order), never "the unit on the tile"; a new rule that reads occupancy must do the same. `TradeRule.Reconcile` runs after every command (deals end on capture, go when the trader dies, homeless traders are rehomed) and `TradeRule.Exchange`/`UpdateDemand` in End turn after upkeep. Partners are the player's own trading cities and `Player.KnownPosts` (enemy cities seen together with their post); the view's `TradePartners` (known posts with their tile, plus the other city of each of the viewer's deals without it, each with its free market less the deals the viewer can't see) keeps `Visibility/TradePreviewCalculator` exact against `Execute` (`TradePreviewCalculatorTests`); `TradeDealView.Trader`/`Paused` and `UnitView.HomeCity` are the owner's only. `CityForecast` deliberately ignores trade.
- **Science (G11a, the owner's model, not a Civ copy):** science is never stocked: a player's science per turn is the ruleset's `science.resource` in their cities' income now (`Engine/ScienceRule.Income`), and every enabled node (`Player.Nodes`, in unlock order; never dropped) takes its `points` of it every turn. `ScienceRule.Balance` runs after every command: while the enabled nodes take more than the income, the newest is switched off; then switched-off nodes are switched on again oldest first while they fit and their prerequisites are on. A unit or building a node lists is locked unless that node is owned and on (`ScienceCalculator.IsUnlocked`); a unit's `replaces` makes a line, and a city produces only the newest unlocked version (`CheckProduce`, `NextProduction` after a unit is made); an existing unit upgrades to it in own territory (`UpgradeUnitCommand`, the tile's city pays `upgradeCost`). A building with `upgrades` is never produced by a city: a builder's job (`UnitJob.UpgradeTo`, `UpgradeBuildingCommand`) makes it on the old building's tile, the city pays its resource cost when the job is done (the finished job waits while it can't), and the new building replaces the old one; rules that ask for a building in any version use `Ruleset.IsKindOf` (the trade post's market still trades). The science commands are dispatched by `ScienceRule.Dispatch`; their previews (`Visibility/SciencePreviewCalculator`) share the rules' checks. `PlayerView.Science` is the viewer's own only. `CityForecast` deliberately ignores the cost paid for a finished building upgrade (as it ignores trade).
- **Map generation** is `Map/MapGenerator` (internal, called by `GameFactory`). It draws from the game's `DeterministicRandom` after the spawns and writes every tile together with its mirror (`GameMap.MirrorOf`), so both halves are the same; spawns are not mirrored (that would tell each player where the opponent started). Its draws use `DeterministicRandom.NextHashed`: anything a client sees in bulk must never come from raw `Next`. Starting tiles stay default terrain and impassable terrain never splits the passable tiles. Its parameters are the ruleset's `map.generation.patches`; tested through `GameFactory.Create` in `Core/Map/MapGeneratorTests`. Rivers come after the terrain (`Map/RiverGenerator`, `map.generation.rivers`): every edge is written with its mirror edge (an edge whose mirror is not an edge isn't used), and an uncrossable edge is laid only while every passable tile stays reachable without crossing one. Changing the generator changes every new game: re-record `GameFactoryTests.Create_KnownSeed_GivesTheRecordedState`. **More players (F10):** two players keep the order above (spawns, then terrain); with three or four the terrain comes first (no reserved tiles), then `Map/SpawnPlanner` gives each player a zone (three: the left edge, then the top and bottom thirds of the right edge; four: the corners clockwise from the top left), keeps the zone's tiles whose row of starting units is passable, and draws (hashed) among those within 5% of a common start value (`PredefinedMapBalanceValidator.StartValue`), so the starts are fair without a mirror that pairs only opposite corners. A map's size per player count is `map.sizes`.
- **Leaving a game of three or more (F10):** a player resigns or is eliminated while two or more stay active; the game goes on. `VictoryRule` (after every command) removes their units, ends every deal their cities host (`TradeRule.EndDeal`), and passes the turn (`EndTurnRule.PassTurn`, which skips inactive seats) when they were the current player; their cities stay, capturable. A new rule that hands something to "the other player" must name a player instead: there may be several.
- **Predefined maps (G18)** are `Map/PredefinedMap` (from `maps/<key>.json`, parsed by `PredefinedMapParser`, as strict as the ruleset parser), passed in `GameSetup.Map`; `GameFactory` then skips generation. `PredefinedMapValidator` (shape) and `PredefinedMapBalanceValidator` (fairness) check it. Unlike a generated map its halves need not be mirrors (the owner wants each side to differ), so fairness is measured: passable tiles stay connected, on a two-player map each resource's yield per half within 15%, every spawn candidate's start value (yields within 3 tiles) within 10% of the mean and both sides' averages within 5%, and each player's own candidates (`spawns`, one group per player from `setup.minPlayers` to `maxPlayers`, each drawn independently) leave the row of starting units passable, no two players' rows share a tile, and on a two-player map the groups lie in the left and right halves. A map is made for as many players as it has groups; on a map for more than two only the starts are compared (no halves), and every group's average within 5% of the best. A new map rule needs a check there, a `PredefinedMapTests` case and `docs/game/maps.md`.
- **The client** (`Govern.Client`) references Core for view types, command records and the view previews only; it never gets `GameState`, `Execute` or `GameSerializer` (`LayerDependencyTests.Client_UsesCoreOnlyForViewsAndPreviews`). Anything public added to Core may be used by the browser, so keep it pure and cheap.
- **Ids and enum values from commands are untrusted:** look a unit type up with `ruleset.FindUnit` (null → `RuleViolations.UnknownUnitType`), an improvement or building with `FindImprovement`/`FindBuilding` and check `Enum.IsDefined` for enums before using them; `ruleset.Unit`/`Terrain` throw on an unknown id, which the Api would return as 500.

## Serialization

- JSON goes through `GameSerializer.Options` only.
- `type` discriminators (`move_unit`, `unit_moved`, …) are a storage and wire format: never rename one.
- Computed properties get `[JsonIgnore]`.
- A breaking change to the shape of `GameState` bumps `GameState.CurrentSchemaVersion` and needs an upgrade in `GameSerializer.DeserializeState` for stored games (e.g. v1 → v2 drops `nextId`; v2 → v3 claims territory and moves the player stockpile into the first city).

## Folders and naming

Whitelisted by `Templates.Core()` and checked by `FolderStructureTests`:

| Folder | Holds |
|---|---|
| `Engine/` | The pipeline: `GameEngine`, `CommandDispatcher`, `CommandResult`, `GameUpdate`, `GameCommand` (base + discriminators), `RuleViolation`/`RuleViolations`, the cross-action `CommandGuardRule` and `VictoryRule`, `DeterministicRandom` |
| `State/` | The snapshot: `GameState`, `GameStatus`, `GameSetup`, `GameFactory`, `Player`, `PlayerId`, `PlayerStatus` |
| `Map/` | Geometry and movement: `HexCoord`, `HexEdge`/`HexSide`, `GameMap`, `Tile`/`TileRivers`/`TileBridges`, `TerrainType`/`TerrainDefinition`, `RiverType`/`RiverDefinition`, `ReachabilityCalculator`, the map and river generators |
| `Units/`, `Cities/` | The things on the map, `UnitType`/`UnitDefinition`/`UnitAbility`, `UnitJob`, `CityProduction`, `UpkeepPriority`, `BuildingDamage` |
| `Economy/` | What is built and gathered: `ResourceType`/`ImprovementType`/`BuildingType` ids, `ResourceAmount`, their ruleset definitions, `YieldCalculator` and `UpkeepCalculator` |
| `Actions/` | Flat; one `XxxAction.cs` per player action with exactly `XxxCommand` + `XxxRule` (`ActionFiles_DeclareExactlyThePrefixedCommandAndRule`) |
| `Events/` | `GameEvent` + events; shared by several actions, so not per action. Types end with `Event` |
| `Visibility/` | Fog of war: `VisibilityCalculator`, `PlayerView` and its parts (`TileView`, `UnitView`, `CityView`, `PlayerSummary`), and the view-based previews (`ViewPreviewCalculator`, `UpkeepPreviewCalculator` with `CityForecast` and `UnitSupply`, `TradePreviewCalculator`), `TradeDealView`, `TradePartnerView` |
| `Serialization/` | `GameSerializer` |
| `Rulesets/` | `Ruleset` (the parsed document and its lookups), its section records (`SetupRules`, `MapRules`, `SpawnRules`, `CityRules`, `TerritoryRules`, `UpkeepRules`, `TradeRules`, `ScienceRules`), `RulesetParser` (strict JSON), `RulesetValidator` (and its `EconomyRulesValidator`, `UpkeepRulesValidator`, `ScienceRulesValidator` parts), `RulesetProblem`/`RulesetParseResult` |
| `Science/` | The science tree (G11a): `ScienceNode` (a ruleset node), `OwnedNode` (a player's node, enabled or switched off), `ScienceNodeChange`, and `ScienceCalculator` (locks, unit lines, upgrades, whether a node can be unlocked), shared by the rules and the client |

- There are no root files.
- Concept folders may get sub-folders when they grow.
- A new top-level folder needs a template change: update `Templates.CoreFolders`, this table and `architecture.md` together.

## Tests

- **Location:** `tests/Govern.UnitTests/Core/<Folder>/XxxTests.cs`.
- **Rules:** tested through `GameEngine.Execute`, with scenarios from `Builders/GameStateBuilder`. Give both players a city or settler (e.g. `WithCapitals()`), otherwise `VictoryRule` ends the game after the first command.
- **Assertions:** `result.ShouldSucceed()` / `result.ShouldFailWith(RuleViolations.X)`.
- **Records holding `ImmutableArray` don't compare structurally.** Compare their elements, or the `GameSerializer` JSON.
