Recurring risks found in the first Govern.Core review (2026-09-27, Plan 1 on feature/game-core-engine):
- **Fog oracles through rejected commands:** rejected commands never change state, so a client can probe freely. `MoveUnitRule` returned `move.occupied` for hidden enemy units anywhere on the map; `unit.not_owned`/`city.not_owned` vs `*.not_found` enumerate enemy ids. Every new rule/error must be checked for "does the error differ based on something the actor cannot see?"
- **Sight vs reach invariant:** pathfinding blocked by units and `City.MinimumSpacing` checks read full state; they are only leak-free while Movement (at min terrain cost) <= Sight and MinimumSpacing - 1 <= settler Sight. Flag new units/terrain that break it.
- **Client preview gap:** `GameEngine.ReachableTiles` takes `GameState`, but the client only gets `PlayerView` (Plan 5 relies on it).
- **STJ:** missing `type` discriminator on an abstract polymorphic base throws `NotSupportedException`, not `JsonException` (500 in minimal-API binding). File-based `dotnet run` apps default to AOT with reflection JSON disabled; add `#:property PublishAot=false` when probing.
- **Branch flow:** `gamecore` was retired 2026-09-30; game work branches from and PRs to `stage`. Stale `gamecore` mentions remained in ci.yml triggers and docs/plans/deferred (follow-ups.md, ruleset-b-store-and-pin.md).

Fixed in the same PR: both oracles, ReachableTiles viewer scoping, JsonException wrapping, schema pre-check, PQ tie-break, CI trigger for gamecore, purity arch tests. Still open: PlayerView-based preview overload (Plan 5), bash-guard does not protect gamecore.

**Why:** hidden information is the core anti-cheat promise of ADR 0004; these leaks pass all unit tests.
**How to apply:** on any Core change, re-run the oracle check per error code, and on Plans 2-5 check the Api maps errors without adding detail and never sends GameState/raw events. See [[convention-sweep-gaps]].

Plan 2 review (2026-09-27, feature/game-lobby: Game/GamePlayer, jsonb state, 5 /api/games endpoints). No critical findings. Checks worth repeating on Plans 3-5:
- `PlayerId` = `GamePlayer.Id` (never a user id); every response with a `PlayerView` must stay free of user ids (`Get_Started_ResponseContainsNoUserIds` pattern).
- Endpoints whose request has a Guid `NotEmpty` validator return 400 but tended to miss `.ProducesValidationProblem()` and `<response code="400">` (Get/Start). Check every new route-id endpoint.
- Race handling via `Revision` concurrency token + unique indexes is correct, but `Task.WhenAll` tests don't deterministically hit the catch branches; ask for a forced race if a new catch path is added.
- jsonb reorders object keys, so anything deserialized from `games.state` needs `AllowOutOfOrderMetadataProperties` (GameSerializer has it; HTTP JSON options do not, so Plan 3 command bodies must go through `GameSerializer.Options`).
- Core `RuleViolations` and Application `GameErrors` share the `game.` code prefix; watch for collisions when Plan 3 maps violations to `Error`.

Plan 3a review (2026-09-27, feature/game-commands: command endpoint, per-user rate limits, unfinished-games cap). No critical findings. Verified, don't re-derive:
- `GameRowLock` makes the command race deterministic: reads aren't blocked, UPDATE ... WHERE revision blocks, EPQ re-check fails -> DbUpdateConcurrencyException -> `game.stale_version`.
- `MapInboundClaims = false` and UseRateLimiter comes after UseAuthorization, so per-user (`sub`) partitions work; the IP fallback in `PerUser` is unreachable.
- `GameSerializer` has `RespectRequiredConstructorParameters` and throws on `null`, so empty/`null`/missing-field bodies are 400 from `GameCommandBody.BindAsync`.
Checks worth repeating: any per-user cap must have a way out for every counted state (joined lobbies can't be left, resigned or expire, so the unfinished-games cap can lock a user out); new 409 codes must also go into the endpoint table rows of games.md, not only the error-code table; a shared rate-limit policy test must hit every endpoint it claims (Join was unasserted); the size cap has two branches (Content-Length and streamed) and each needs a test.

Plan 3b review (2026-09-28, feature/game-live-updates: SSE stream, opaque view version, random ids). Critical found:
- **RNG outputs must never reach clients.** Ids drawn with `DeterministicRandom.Next(1, int.MaxValue)` expose ~31 bits of a SplitMix64 output; the mix is invertible, so two consecutive own ids recover `RngState` by brute-forcing the 2^33 quotient (verified: ~3 s, 8 threads, clang). That reveals the enemy spawn tile (drawn right after P0's ids) and every future id (index in the stream = opponent's creation count). Fix pattern: pass the 64-bit draw through SHA-256 (or a keyed hash) before truncating it to an id.
- `MyGameItem.UpdatedAt` (and the list order by it) changes on hidden commands, so polling `GET /api/games` leaks when and how often the opponent acts. It was there before 3b, but it contradicts the "timing doesn't leak" claims in ADR 0005.
Verified OK, don't re-derive: events dispatch in `SavedChangesAsync` with no explicit transactions (post-commit, so subscribe-before-read is sound); .NET `ChainedRateLimiter.IdleDuration` is null if any child is busy, else the minimum; `ToServerSentEvents` cancels then drains a pending MoveNext before `DisposeAsync`.
**How to apply:** for any id, token or value derived from game randomness that a client sees, ask "how many bits of raw PRNG output does this expose?". For any timestamp or counter on a game row that a client sees, ask "does a hidden action change it?".

Plan 3c review (2026-09-28, feature/game-lobby-lifecycle: leave, cancel, expiry sweep, seat quota, activity_at). No critical findings. Medium: games can now be deleted (cancel, sweep), so a join that loaded the lobby before the delete inserts a `game_players` row whose FK check waits on the delete and then fails with 23503. That is a plain `DbUpdateException`, not a concurrency or unique-violation error, so it becomes a 500. `IDbExceptionClassificationService` only knew unique violations.
**How to apply:** whenever a change adds a path that deletes a parent row (games, users), check every concurrent child insert (seats, and later outbox, messages) for FK-violation handling, and ask for a GameRowLock race test with the delete as the winner. The `GameRowLock` races with `Task.WhenAll` don't pin which writer wins, so they don't guarantee that the reevaluation branch runs. To force the order, fire the writers one at a time and wait for N lock waiters between them. Verified OK, don't re-derive: `ActivityAt` moves only on Phase/CurrentPlayerId changes, and the sweep's repeated predicate plus EPQ keeps a lobby that was just joined.

Plan 5a review (2026-09-29, feature/core-player-view: TileView without coord, CityView, view-based previews). No production bug; refactored AttackRule/FoundCityRule/CommandGuardRule keep the original error order exactly. Verified, don't re-derive: no unit stacking (move/spawn/capture all require an empty tile), so `UnitAt` order can't differ between state and view; view Dijkstra equals state Dijkstra because every tile within budget is within the mover's own sight (plains only, cost 1); `PlayerSummary` is a class so `FirstOrDefault(...)?.Status` is null-safe.
Checks worth repeating:
- **Vacuous Shouldly chains:** `x?.Code.ShouldBe(expected)` skips the assertion when `x` is null. Ask for `(x?.Code).ShouldBe(expected)`. Found in GameEnginePreviewTests and GameEventsReader.
- Parity theories need scenarios on each branch where state and view differ or the shared check branches: own city inside reach, attack on own city (`cityOwner` branch), a hidden enemy at sight + 1, settler with 0 movement. New terrain (cost > 1 or impassable) must add parity scenarios.
- Remaining view leaks: city names `City N` = founder's city count at founding (reveals hidden enemy cities). Enemy `MovementLeft` was closed by `UnitView` (2026-09-30).

UnitView review (2026-09-30, feature/unit-view). No critical. Verified, don't re-derive: `Unit` has no field besides Id/Owner/Type/Position/MovementLeft, so `UnitView` hides everything owner-only; clients never receive `GameEvent`s (SSE sends view snapshots only); the only view-side reader of `MovementLeft` is `ViewPreviewCalculator.OwnUnit` (own units only) and `UnitPanel` (own-only branch). Check on later view changes: `Client_UsesCoreOnlyForViewsAndPreviews` is a deny-list, so state types the client stopped using (`Units.Unit`, `Cities.City`) are not locked out unless added to its regex.

G4 terrain review (2026-09-30, claude/project-thread-ajx0tr: MapGenerator, sight bonus, lenses). Found:
- **Visible content drawn with `DeterministicRandom.Next`** (= raw SplitMix64 output % range) leaks raw low bits to clients: generated terrain is visible, so every patch-seed draw exposes `raw % tileCount` (low 3 bits exact at 280 tiles, low 6 at 1600). Same class as the 3b id leak. Anything a client can see that is drawn from the game RNG must go through a hashed draw (SHA-256 like `GameState.NewId`).
- A generator that reserves hidden positions (enemy spawn and its mirror) makes visible output depend on hidden state: measured ~1 bit (enemy spawn candidates 48 -> ~24 on 20x14) from "both tiles plains"; with a recovered RNG state it would be exact.
- Measured cost (Release): 40x40 default v2 ~28 ms/game, almost all in the per-impassable-placement flood fill; worst valid ruleset ~42 ms. Blank map 0.3 ms.
Verified OK, don't re-derive: odd-r point mirror (W-1-c, H-1-r) is an exact hex isometry only for even height (any width); connectivity guarantee holds on odd heights too (flood runs on the real map); map size is not user-controlled (Game.cs uses ruleset defaults); previews stay exact with cost-2/impassable terrain because every path tile is within movement/cheapest <= sight.
**How to apply:** for any new randomised, player-visible content (maps, loot, events), ask "is it drawn from a hashed stream, and does it depend on anything hidden?".

G9 combat review (2026-09-30, claude/project-thread-3nf3bn: health as Unit.Damage, CombatCalculator, ranged, healing, two-step attack). No critical. Verified, don't re-derive: forecast = Execute (same CombatCalculator, integer maths, `Roll` skips the draw only when min == max, deterministic); `AttackRule.Check` still tests distance before owner, so no oracle; visibility is pure radius (no line of sight), so range <= sight keeps ranged targets visible; damage rolls use `NextHashed` (41 values, negligible bias); `GameSerializer` ignores unknown members but requires ctor params (old client + new Api is fine, new client + old Api would fail on `health`; release deploys the Api first).
Checks worth repeating:
- **Health is public, so any rule keyed on hidden state that changes health leaks it.** Healing = "movement still full" tells the opponent whether a hurt visible unit spent any movement (e.g. slipped into fog and back), which UnitView hides MovementLeft to prevent.
- Validator has no upper bounds on combat numbers (strength, maxHealth, damage.max, perStrengthPoint): `baseStrength * (maxHealth + health)` and `raw * rollPercent` can wrap. Ask for caps like the map bounds.
- `Unit.Damage` is absolute while games aren't pinned: a later ruleset lowering maxHealth leaves live units at health <= 0.
- v1/v2 ruleset files no longer parse with current Core (new required fields); matters when G3b pins games to versions.

G10a review (2026-10-01, claude/project-thread-0njb5y: jobs, improvements, buildings, bridges, stockpile, ruleset v5). No critical. Verified, don't re-derive: work areas can't overlap (FoundCity forbids distance < minimumSpacing, validator wants spacing > 2*workRadius), so `FirstOrDefault` city per job is unique; bridge preview is exact because `build_bridge` sight >= workRadius + 1; bridges/improvements are only on Visible TileViews, so hidden enemy construction doesn't move the view fingerprint; all new state fields are WhenWritingNull/optional ctor params.
Checks worth repeating:
- **Client numbers that ignore cross-mechanic diversion:** CityPanel's turns-left used the full production while a job on the city's ground was consuming it. When a mechanic diverts a resource, check every panel that forecasts with it.
- Docs drift on edge objects: bridges are stored on one owner tile, so "seen while both banks are visible" claims are wrong (only the owner tile matters).
- Heal-gating keyed on hidden state (job) widens the accepted heal leak; the docs' "known leak" sentence must be kept in sync.
- Validator gaps to ask about on new radius-like fields: is the owner guaranteed to see what the field covers (cities.sight vs workRadius)?

G5/G7/G8a PR 1 review (2026-10-01, claude/project-thread-qjb1fk: territory, per-city stock, schema 3). Found:
- **Edge-stored data on an unexplored neighbour:** rivers live on one tile of each edge (`HexEdge.Between`), and an unexplored TileView has no Rivers. Own territory (maxRadius 3) reaches past city sight (2), so a border tile's W/SW/SE river edge can be stored on an unexplored tile: `GameEngine.CityIncome` undercounted water vs EndTurn (verified with a scratch test: 50 vs 55). Any preview summing per-tile data from the view must check "who stores the edge, and is that tile always known?".
- Border growth on visible tiles exposes an enemy city's growth-resource income (culture buildings that CityView hides).
Verified OK, don't re-derive: territory rules read only the unit's tile and neighbours (always visible since sight >= 1); NextTile is fully ordered (no HashSet order leak); FoundCity/BuildImprovement/Bridge previews match Execute; client `ApiJson` is not strict, so dropping a PlayerView ctor param doesn't break an old cached client.

G8a review (2026-10-01, claude/project-thread-qjb1fk PR 2: resource costs, upkeep, supply, building health, v7). No critical. Found:
- **Preview caveats narrower than the code:** `CityForecast.MissingToBegin` ignores that EndTurn skips `Produce` for a city whose production fed a job (`usedCities`), and CityPanel's ProgressBar `PerTurn` ignored "unpaid item gains nothing" and the post-upkeep building damage Produce uses. Same class as the G10a diversion check: for every new end-turn skip/wait, check each preview and panel number.
- Starvation/no-heal on visible enemy units in their territory exposes the hidden city stock shortfall; the "known, accepted leak" paragraph in game-logic.md fog section must list it.
Verified OK, don't re-derive: `TileView.TerritoryCity` is own territory only, so UnitSupply on enemy land falls through to land supply exactly like `UpkeepRule.PayingCity`; supply preview exact via validator `sight >= supplyRadius + 1` (edge rivers on the outer ring); upkeep never uses hidden data; enum input is string-only (`allowIntegerValues: false`) plus `Enum.IsDefined`; costs can't use growthResource, so territory growth between upkeep and production can't change the answer.

F11a/F11b review (2026-10-01, claude/project-thread-0w25hf: EventsFor, per-seat GameLogEntry, log in GetGameResponse, animations). Found:
- **`WhenWritingNull` on a ctor param without a default breaks `GameSerializer` reads:** it has `RespectRequiredConstructorParameters`, so a stored event with the null omitted throws `JsonException` (missing required properties) in the EF converter -> 500 on every read of that seat's log window. Verified with a scratch round-trip of `UnitAttackedEvent` with AttackerId/From null. Nullable params that can be omitted need `= null` defaults (like TileView). Client `ApiJson` (web defaults) reads it fine, so client tests don't catch it.
- **Ids in filtered events can exceed the view:** `TerritoryGrewEvent.CityId` names the enemy city owning a border tile (TileView hides TerritoryCity for enemies), `BridgeBuiltEvent.From`/`UnitId` pass when only `To` is seen (hidden worker tile), `UnitCreatedEvent.CityId` when the unit spawns on a seen neighbour of a hidden city. For every event field, ask "does the view show this for an enemy?".
- SSE dedupes on (phase, seats, view version) only; a move passing through sight (start and end in fog) changes no view, so its log entry waits for the next push.
Verified OK, don't re-derive: MaxPlayers = 2, so a hidden attacker only reaches the defender (whose health drop already equals DamageDealt); v7 has every sight >= 2 and archer range 2, so the hidden-attacker branch is unreachable today (validator only caps range by the attacker's own sight); LogLength race is covered by the game revision token.

G10c review (2026-10-01, feature/G10c-building-sites: Tile.Building, City.ProducingBuildingSite, BuildingSites preview, placing mode). No critical. Verified, don't re-derive: own territory is always Visible (VisibleTiles adds it) and its outer ring is always Explored (UpdateExplored's TerritoryRing, run after every Execute), so a site check over any own-territory tile and its neighbours' terrain is exact from the view; a reservation can only sit in the reserving city's own territory and is cleared by SetProduction/capture/completion, so BuildImprovement's `state.Cities.Any(site == pos)` can't see an enemy reservation (NotInTerritory comes first); ConstructionRule re-runs CheckPlacement each turn, so a captured enemy job on a newly reserved tile is dropped.
Checks worth repeating:
- **Rule reads beyond "unit tile + neighbours":** a rule over a whole territory relies on the territory-visible + ring-explored invariant, which isn't in the validator or the rule file's fog list; ask for it to be documented and for a parity scenario whose site neighbour is past city sight (territory radius >= 2), since the default builder territory (radius 1) never reaches past sight.
- **Hand-copied check order** (`SiteCheckOrder` mirrors `CheckSite`) used to pick a "closest" reason: the parity test only checks membership, so a reorder drifts silently.
- **Re-pick UIs that highlight the current choice** send no-op commands that still emit events (log noise).
- game-logic.md fog section lists what the view shows per tile; every new TileView/CityView field must be added there, not only in .claude/rules/game-core.md.

F19 review (2026-10-03, claude/project-thread-14v1na: Unit.Destination, AutoMoveRule, PathFinder, DestinationPath preview). No critical. Verified, don't re-derive: plan over Explored ∪ Visible equals the view's knowledge (explored TileView = terrain + rivers, bridges/units/cities only on visible tiles, edge owner of a path step is always a known tile); real step cost can only be <= planned (hidden bridges), never higher; the walk's "hidden blocker stops for this turn, keeps the order" branch is unreachable with 2 players (sight >= 1, so the blocker enters the unit's sight one step earlier and EnemySighted ends the order first).
Checks worth repeating:
- **Parity theories built without explored tiles:** `GameStateBuilder` players had `Explored = []`, so `GameEnginePreviewTests` scenarios never contain explored-but-not-visible tiles; any preview whose rule reads Explored needs scenarios with `WithMapExplored` (hidden unit/city/bridge on a known tile).
- **Moves made inside the opponent's command** (turn-start auto walks in PassTurn) let the opponent tell automated moves from manual ones and predict the next walk; the docs' accepted-leak list and player rules must say so.
- Enum names in docs: GameSerializer/ApiJson use camelCase (`enemySighted`), not snake_case.

G17 trading review (2026-10-03, claude/project-thread-u8gkn1: markets, traders, routes, deals, v10). G17b (2026-10-05, v13) removed routes: `TradeRoute*`, `on_route` and the route-opened filters below are history; deals now belong to traders (`TradeDeal`, `TradeDealView`, `TradePartnerView`), traders share tiles (`HolderAt`, `DefenderAt`). Found:
- **Null elements in command arrays:** GameSerializer accepts `[null]` inside `ImmutableArray<ResourceAmount>` (RespectRequiredConstructorParameters doesn't cover elements; verified with a scratch probe), so `ProposeDeal.Gives=[null]` NREs in `TradeCalculator.CheckDeal` -> 500. Any new command with an array of reference-type records needs a null-element check (or struct elements).
- **Events for routes the host never saw:** `TradeRouteChangedEvent` is filtered by Owner/HostOwner only, so Closed on a not-yet-opened route reaches the host (reveals the route and its hidden home city id). Filter host-side events on "opened" like `TradeRouteView.From`.
- `TradeRouteView.HostMarket/HostDemand` are live state, not "learned at the post": they keep updating while the trader is dead/away (demand includes unpaid upkeep, so it shows host starvation).
- Units with `trade` + another ability aren't refused with `trade.on_route` by Attack/FoundCity/BuildImprovement/BuildBridge; only Move/SetDestination check. Ask for a guard or a validator rule.
Verified OK, don't re-derive: Open/Propose/Accept previews match the engine (hosted unopened routes carry no deal; proposals commit only the home city); route ids come from AllocateId (hashed); Exchange order (AcceptedTurn, id) deterministic; buildings are never removed, so PostTile is stable until capture (which closes the route).

G18 review (2026-10-03, claude/project-thread-69iq1k: PredefinedMap, MapChoice, MapPoolService, maps/basin.json). No critical. Found:
- **Public spawn candidates shrink the opponent's start to n known tiles** (basin n=3; the validator allows n=1, which reveals it exactly). Docs claimed only "your own start doesn't tell you which". Ask for a minimum candidate count and an accepted-leak line whenever spawn options come from public data.
- STJ `RespectNullableAnnotations` does not cover collection elements: `rows: [null]` gives a NullReferenceException from `PredefinedMap.Parse` (verified), not a problem. Check element nulls in every strict document parser.
- `Lazy<T>` caches a load exception, so "an invalid file stops the first request" really means every request until restart.
Verified OK, don't re-derive: right-side spawn row = mirror of the left row (W-1-c-k), so the left-only spawn check covers both sides via terrain symmetry; `random` resolves with crypto RNG in Application (not the seed); the state keeps its own map copy.

F20 review (2026-10-04, PR #61 claude/builder-lock-camera-map-polish-y5nkz6: ExploreCommand, builder lock/CancelJob, asymmetric Basin, WASD pan). No critical. Verified, don't re-derive: CheckExplore = Execute (same guard order; frontier "not Explored and not Visible" equals TileView Unexplored; Knowledge.StepCost equals KnownStepCost); Explore loop terminates (validator movementCost >= 1); with sight >= movement the first leg's frontier costs >= movement, so a second leg only follows a partial leg (a step cost > movement left).
Checks worth repeating:
- **Re-planning inside one command uses mid-walk sight that UpdateExplored never records** (Explored is updated once per Execute, from the final positions). Any new multi-leg walk should either update Explored per leg or plan once.
- Global window key handlers in board JS: check macOS Cmd-held keyup loss, focus scope (dialogs, dropdown typeahead) and the per-frame hover raycast they trigger on the full ground mesh.
